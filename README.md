## Навигация по проекту

Наш репозиторий структурирован следующим образом:

* **`RAG/`** — Ядро нашей поисковой системы:
* **`chunker/`** — Модуль семантического анализа и разбиения кода.
* **`parsers/`** — Специализированные модули под каждый язык (`py`, `jsts`, `cpp`, `go`, `java`) на базе Tree-sitter и ast.
* `chunk.py` — Контракт данных и структура объекта `Chunk`.
* `utils.py` — Утилиты для обхода директорий и нормализации путей файлов.


* **`chroma_db/`** — Векторная база данных Chroma.
* **`data/chunks.jsonl`** — Автоматический бэкап извлеченных чанков (используется для контроля данных и инициализации полнотекстового поиска).
* **`index.py`** — Сквозной пайплайн индексации (сбор чанков, генерация эмбеддингов батчами и сохранение в БД).


* **`accuracy_checking/`** — Изолированный модуль оценки качества работы поискового движка. Содержит тестовые пулы вопросов (`eval_questions.json`), генератор результатов и тестовые запросы.
* **`dataset/`** — Целевая папка, куда складываются индексируемые исходники (`gymhero`).
* **`score.py`** — Скрипт на корневом уровне для расчета финальных метрик точности ответов (Accuracy).

## Как запускается индексация

Пайплайн индексации полностью готов, переведен на английские логи/комментарии и снабжен механизмом автоматической очистки старых индексов во избежание дублирования путей.

Запуск выполняется из корня репозитория. В качестве обязательного аргумента передается путь к целевой папке с кодом:

```bash
python RAG/index.py dataset/gymhero

```

### Что происходит при запуске:

1. **Сканирование и парсинг:** Скрипт ищет файлы поддерживаемых языков в указанной папке, извлекает классы, функции и методы с помощью ast и tree-sitter.
2. **Создание бэкапа:** Структура чанков дублируется в локальный файл `RAG/data/chunks.jsonl`.
3. **Очистка базы данных:** Скрипт очищает старую базу данных во избежание дубликатов кода при повторном запуске.
4. **Генерация векторов:** Создаются эмбеддинги через модель `BAAI/bge-m3` батчами по 8 элементов и сохраняются в ChromaDB.

## Что осталось сделать (План работ)

### 1. Реализация `RAG/searcher.py` (Модуль гибридного поиска)

Для работы с кодом чисто векторный поиск не всегда эффективен, так как он может упускать точные названия методов и переменных. Мы переходим на **гибридный поиск (Dense + Sparse)**.

* **Логика:** Совмещение семантического поиска ChromaDB и ключевого полнотекстового поиска через библиотеку `rank_bm25` (развернутую поверх нашего бэкапа `chunks.jsonl`).
* **Управление:** Поиск должен принимать параметр веса `alpha` (от `0.0` до `1.0`). При `alpha = 0.2` приоритет будет отдаваться точному совпадению строк (BM25), при `alpha = 0.8` — смысловому контексту запроса. Результаты будут объединяться методом линейного рескоринга.
