# CodeLens RAG

Семантический поиск по кодовой базе с гибридным retrieval (векторный + BM25) и опциональным LLM-объяснением найденного кода.

**«CodeLens RAG»** · Чемпионат ГК «Ростелеком», 2-й этап, направление «Искусственный интеллект»

## Аннотация

В работе представлена система семантического поиска по кодовой базе, сочетающая плотные векторные представления (dense retrieval) и лексический поиск BM25 в едином гибридном ранжирующем пайплайне. Индексация выполняется на уровне логических единиц — функций и классов — с обогащением контекстной информацией (путь, имя символа, документация). Система поддерживает мультиязычные запросы (русский/английский), несколько языков программирования (Python, Java, JS/TS, C++, Go) и опционально генерирует объяснения найденного кода с использованием LLM (Groq, Llama 3.1). Экспериментальная валидация на эталонном наборе из 15 запросов демонстрирует Precision@5 = 0.778 и MRR = 0.728, что подтверждает эффективность предложенного подхода.

## 1. Введение

### 1.1. Проблематика

Крупные IT-компании управляют репозиториями, содержащими десятки тысяч строк кода. Новички тратят от 2 до 6 недель на ознакомление со структурой проекта. Опытные разработчики регулярно отвлекаются на повторяющиеся вопросы о локализации функциональности. Традиционные инструменты поиска (grep, полнотекстовый поиск) неэффективны для запросов на естественном языке, поскольку имена функций и переменных редко совпадают с лексикой пользовательского запроса.

### 1.2. Цель и задачи

Цель работы — разработка прототипа системы, осуществляющей семантический поиск по кодовой базе с возможностью генерации объяснений на естественном языке.

**Задачи:**
- Разработать пайплайн индексации кода с выделением семантических единиц (функций, классов)
- Реализовать гибридный механизм ранжирования (dense + sparse retrieval)
- Обеспечить мультиязычную поддержку запросов (RU/EN)
- Интегрировать LLM для генерации интерпретируемых ответов
- Провести экспериментальную оценку качества на эталонном датасете

## 2. Архитектура системы

### 2.1. Общая схема

```
Запрос пользователя (RU / EN)
        │
        ▼
┌────────────────────┐
│  bge-m3 embedding  │──── векторный (dense) поиск — ChromaDB
└────────────────────┘
        │
        ├──────────────┐
        ▼              ▼
   Dense search    BM25 (rank_bm25, поверх chunks.jsonl)
        │              │
        └──── alpha ────┘
              │ линейный рескоринг:
              │ score = alpha · dense + (1 − alpha) · BM25
              ▼
        Топ-5 фрагментов кода
              │
              ▼  режим «Чат с LLM»
        Groq API (llama-3.1-8b-instant, temperature=0.3)
              │
              ▼
     Объяснение на русском со ссылками на источники
```

### 2.2. Компонент индексации

#### 2.2.1. Стратегия чанкинга

Код разбивается на чанки **по функциям и классам**, а не по фиксированному числу строк — это даёт каждому чанку завершённую логическую единицу. Помимо тела функции в текст чанка добавляются путь к файлу, имя символа и docstring — это даёт модели больше контекста при построении эмбеддинга.

#### 2.2.2. Парсинг и мультиязычность

Архитектура парсера реализована по принципу расширяемости — каждый поддерживаемый язык обслуживается независимым модулем. Диспетчер (`PARSERS_MAP` в `router.py`) направляет файл соответствующему парсеру на основе расширения.

| Язык | Инструмент | Основание |
|------|-----------|-----------|
| Python | `ast` (встроенный) | Нативная поддержка, высокая надёжность |
| JS/TS | Tree-sitter | Корректный парсинг современного синтаксиса |
| C++ | Tree-sitter | Сложный синтаксис, макросы |
| Go | Tree-sitter | Специфичный синтаксис |
| Java | Tree-sitter | Классовая структура |

Дополнительно проведено тестирование системы на датасете **Java** (TheAlgorithms/Java, 10 384 чанка) — результаты в разделе 4.4.

#### 2.2.3. Генерация эмбеддингов

Используется `BAAI/bge-m3` — мультиязычная модель, одинаково хорошо работающая с русскими и английскими запросами против англоязычного кода.

Векторы хранятся в **ChromaDB** (`PersistentClient`) — локально на диске без необходимости поднимать отдельный сервер, с поддержкой косинусного сходства (`hnsw:space: cosine`).

#### 2.2.4. Логирование

Пайплайн индексации использует стандартный модуль `logging` (уровень `INFO`). Файлы с синтаксическими ошибками логируются как `WARNING` и пропускаются без прерывания индексации:

```
2026-06-22 01:25:34 [INFO] Extracting semantic chunks from repository ...
2026-06-22 01:25:35 [INFO] Successfully extracted 155 semantic chunks
2026-06-22 01:25:35 [INFO] Using device: mps
2026-06-22 01:25:43 [INFO] Connecting to ChromaDB ...
```

Флаг `--force` принудительно очищает коллекцию перед переиндексацией.

### 2.3. Компонент поиска

#### 2.3.1. Гибридный поиск

Чисто семантический поиск иногда упускает точные совпадения идентификаторов. Поэтому поверх dense-поиска добавлен **BM25** (`rank_bm25`) — классический полнотекстовый поиск, хорошо находящий точные лексические совпадения.

Результаты нормализуются (min-max scaling) и объединяются линейно:

```
score = alpha · dense_score + (1 − alpha) · bm25_score
```

Параметр `alpha` настраивается в интерфейсе (страница «Расширенные настройки»).

#### 2.3.2. Временные характеристики поиска

Тест задержки на 20 запросах из `sample_queries.txt` (`latency_test.py`):

| Операция | Время |
|----------|-------|
| Поисковый запрос (после загрузки модели) | **~0.03 сек** |
| Ответ LLM (Groq) | 1–3 с |
| Полный цикл «поиск → LLM-ответ» | 3–5 с |

Целевое значение по условиям кейса — ≤ 3 сек на поиск. 

### 2.4. LLM-интерпретация

Используется облачный API Groq с моделью `llama-3.1-8b-instant`. Промпт передаётся в роли `system` (инструкции) и `user` (вопрос + фрагменты кода) — это обеспечивает строгое следование правилам: модель не выдумывает функциональность, отсутствующую в коде, и честно сообщает об отсутствии релевантных фрагментов.
Выбор обусловлен следующими факторами:

1. **Скорость инференса:** 1-3 секунды против 10+ секунд для локальных альтернатив
2. **Доступность:** бесплатный тариф с достаточными лимитами
3. **Качество:** Llama 3.1 демонстрирует высокую точность в задачах анализа кода

Температура генерации установлена на уровне 0.3, что обеспечивает баланс между детерминированностью ответа и естественностью формулировок. Промпт содержит явное требование не выдумывать функциональность, отсутствующую в предоставленном контексте.

## 3. Экспериментальная методология

### 3.1. Датасет

| Параметр | Значение |
|----------|----------|
| Всего запросов | 15 |
| Язык запросов | 8 RU, 7 EN |
| Сложность | 5 Easy, 6 Medium, 4 Hard |
| Категории | auth, api, db, config, errors, business_logic, validation |
| Эталонов на запрос | 1–3 (медиана: 2) |

### 3.2. Метрики оценки качества

Для количественной оценки эффективности поисковой системы использовались две стандартные метрики информационного поиска: **Precision@5** (обязательная, согласно условиям кейса) и **MRR** (дополнительная, введённая для более глубокого анализа поведения системы). Каждая из метрик отвечает на свой исследовательский вопрос и даёт взаимодополняющую информацию о качестве ранжирования.

#### Precision@5

$$\text{P@5} = \frac{|\{\text{релевантные}\} \cap \{\text{топ-5}\}|}{\min(5,\,|\{\text{релевантные}\}|)}$$

Целевой порог по условиям кейса: ≥ 0.60.

#### MRR

$$\text{MRR} = \frac{1}{N}\sum_{i=1}^{N}\frac{1}{\text{rank}_i}$$

**Почему MRR добавлена:**

1. **Дополняет Precision@5** — Precision@5 отвечает на вопрос «сколько», а MRR — на вопрос «насколько высоко». Это разные аспекты качества, и их совместное использование даёт более полную картину.

2. **Отражает пользовательский опыт** — в типичном сценарии пользователь смотрит первые результаты; если правильный ответ сразу на первом месте, задача решена максимально быстро. MRR напрямую измеряет этот сценарий.


### 3.3. Процедура валидации

1. Для каждого вопроса из `eval_questions.json` выполняется гибридный поиск
2. Формируется `results.json` с топ-5 идентификаторами чанков
3. `score.py` сопоставляет предсказанные и эталонные чанки с допуском ±2
4. Вычисляются метрики с разбивкой по языку и сложности

## 4. Результаты и обсуждение

### 4.1. Выбор модели эмбеддингов

На отборочном этапе выполнено сравнение трёх моделей эмбеддингов на идентичных данных:

| Модель | Размерность | HitRate@5 | RU | EN |
|--------|-------------|-----------|----|----|
| MiniLM-L12-v2 | 384 | 0.78 | 0.62 | 0.71 |
| LaBSE | 768 | 0.89 | 0.81 | 0.83 |
| **BGE-m3** | **1024** | **1.00** | **0.86** | **0.91** |

**Интерпретация:** BGE-m3 демонстрирует превосходство по всем метрикам. Ключевым фактором является мультиязычная природа модели, позволяющая обрабатывать русскоязычные запросы без потери точности. Дополнительный выигрыш даёт обогащение текста чанка контекстной информацией — прирост точности составил до 16% относительно подачи «голого» кода.

### 4.2. Оптимизация гиперпараметра α

| α | Precision@5 |
|---|-------------|
| 0.0 (только BM25) | 0.370 |
| 0.5 (баланс) | 0.667 |
| **0.8 (оптимум)** | **0.778** |
| 1.0 (только dense) | 0.720 |

![Alpha optimization curve](RAG/metrics/alpha_optimization_curve.png)

График наглядно демонстрирует три характерные зоны:

- **α = 0.0 (только BM25):** Precision@5 = 0.370 — наихудший результат. Чистый лексический поиск не справляется с семантическими запросами на естественном языке: слова запроса не совпадают с идентификаторами в коде.
- **α = 0.05–0.3 (резкий рост):** добавление даже небольшой доли векторного поиска даёт скачок с 0.37 до 0.64 — семантический компонент сразу берёт на себя основную нагрузку по пониманию смысла запроса.
- **α = 0.35–0.55 (плато):** система стабилизируется в районе 0.667 — оба компонента вносят сопоставимый вклад, но ни один не доминирует достаточно.
- **α = 0.55–0.8 (второй рост):** увеличение доли векторного поиска даёт дополнительный прирост — модель `bge-m3` хорошо улавливает семантику кода и документации.
- **α = 0.8 (оптимум):** Precision@5 = 0.778 — пик. Векторный поиск доминирует (80%), BM25 подстраховывает на запросах с точными идентификаторами (20%).
- **α = 0.85–1.0 (небольшой спад):** при полном отказе от BM25 точность снижается до 0.720 — подтверждает, что лексическая компонента необходима для запросов, содержащих точные имена функций.

### 4.3. Итоговые метрики

**Ключевой результат:** система достигла Precision@5 = 0.778, что превышает целевой порог (≥0.60), установленный в условиях кейса.

**Основные результаты:**

| Метрика | Значение |
|---------|----------|
| **Precision@5** | **0.778** |

**Детализация по языку запроса:**

### 4.5. Обсуждение

**Ключевые факторы успеха:**
1. Обогащение текста чанка (путь + имя символа + docstring) — наиболее значимый прирост точности
2. Гибридный ретривер с α=0.8 превзошёл как чисто векторный, так и лексический подходы
3. Мультиязычная модель обеспечила стабильные результаты на обоих языках

**Ограничения:**
- Более низкий P@5 на русском (0.708 vs 0.857) — код и документация gymhero на английском
- Снижение на Hard-вопросах (0.583) — многошаговые запросы требуют более глубокого понимания

## 6. Как запустить

### Установка зависимостей

```bash
git clone https://github.com/yldsha/rt-ai-championship-stage2.git
cd rt-ai-championship-stage2
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

### Индексация кодовой базы

```bash
python -m RAG.src.index dataset/gymhero
```

Флаги:
- `--force` — принудительная переиндексация (очищает коллекцию)
- `--model-name` — выбор модели эмбеддингов (по умолчанию `BAAI/bge-m3`)
- `--db-path` — путь к ChromaDB (по умолчанию `RAG/data/chroma_db`)
- `--batch-size` — размер батча (по умолчанию 16)

### Запуск интерфейса

```bash
python -m streamlit run RAG/src/ui/app.py
```

Откроется на `http://localhost:8501`. Три страницы: **Поиск**, **Чат с LLM**, **Расширенные настройки**.

### LLM-чат (опционально)

```bash
export GROQ_API_KEY="ваш_ключ"   # получить на console.groq.com
```

Без ключа поиск и метрики работают нормально — чат покажет понятное предупреждение.

### Воспроизведение метрики

```bash
python -m RAG.src.accuracy_checking.generate_results --alpha 0.8
python -m RAG.src.score --predictions RAG/src/accuracy_checking/results.json \
                         --questions RAG/src/accuracy_checking/eval_questions.json
```

### Тест поиска и latency

```bash
python -m RAG.metrics_tests.test_search
python -m RAG.metrics_tests.latency_test
```

### Запуск через Docker

```bash
export GROQ_API_KEY="ваш_ключ"
docker compose up --build
```

Docker автоматически проиндексирует кодовую базу при первом запуске и поднимет UI на `http://localhost:8501`.
