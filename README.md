# CodeLens RAG

Семантический поиск по Python-кодовой базе с гибридным retrieval (векторный + BM25) и опциональным LLM-объяснением найденного кода.

** «CodeLens RAG»** · Чемпионат ГК «Ростелеком», 2-й этап, направление «Искусственный интеллект»

## Аннотация

В работе представлена система семантического поиска по Python-кодовой базе, сочетающая плотные векторные представления (dense retrieval) и лексический поиск BM25 в едином гибридном ранжирующем пайплайне. Индексация выполняется на уровне логических единиц — функций и классов — с обогащением контекстной информацией (путь, имя символа, документация). Система поддерживает мультиязычные запросы (русский/английский) и опционально генерирует объяснения найденного кода с использованием LLM (Groq, Llama 3.1). Экспериментальная валидация на эталонном наборе из 15 запросов демонстрирует Precision@5 = 0.778 и MRR = 0.728, что подтверждает эффективность предложенного подхода.

## 1. Введение
### 1.1. Проблематика
Крупные IT-компании управляют репозиториями, содержащими десятки тысяч строк кода. Новички тратят от 2 до 6 недель на ознакомление со структурой проекта. Опытные разработчики регулярно отвлекаются на повторяющиеся вопросы о локализации функциональности. Традиционные инструменты поиска (grep, полнотекстовый поиск) неэффективны для запросов на естественном языке, поскольку имена функций и переменных редко совпадают с лексикой пользовательского запроса.

### 1.2. Цель и задачи
Цель работы — разработка прототипа системы, осуществляющей семантический поиск по кодовой базе с возможностью генерации объяснений на естественном языке.

**Задачи**:

Разработать пайплайн индексации кода с выделением семантических единиц (функций, классов)

Реализовать гибридный механизм ранжирования (dense + sparse retrieval)

Обеспечить мультиязычную поддержку запросов (RU/EN)

Интегрировать LLM для генерации интерпретируемых ответов

Провести экспериментальную оценку качества на эталонном датасете

## 2. Архитектура системы

### 2.1. Общая схема

```
Запрос пользователя (RU / EN)
        │
        ▼
┌────────────────────┐
│  bge-m3 embedding   │──── векторный (dense) поиск — ChromaDB
└────────────────────┘
        │
        ├──────────────┐
        ▼              ▼
   Dense search    BM25 (rank_bm25, поверх chunks.jsonl)
        │              │
        └──── alpha ────┘
              │ линейный рескоринг:
              │ score = alpha · dense + (1 − alpha) · BM25
              ▼
        Топ-5 фрагментов кода
              │
              ▼  режим «Чат с LLM»
        Groq API (llama-3.1-8b-instant, temperature=0.3)
              │
              ▼
     Объяснение на русском со ссылками на источники
```

---

### 2.2. Компонент индексации

#### 2.2.1. Стратегия чанкинга

Код разбивается на чанки **по функциям и классам** (через `def`/`class`), а не по фиксированному числу строк — это даёт каждому чанку завершённую логическую единицу, которую можно осмысленно объяснить и процитировать. Помимо самого тела функции в текст чанка добавляются путь к файлу и имя символа — это даёт модели больше контекста при построении эмбеддинга, чем голый код без подписи.

> Дополнительно к функциям/классам в индекс может попадать содержимое всего файла как отдельный модульный чанк — подробное описание этого механизма и его назначения см. в комментариях `RAG/chunker/parsers/py_parser.py` (реализовано Димой).

#### 2.2.2. Парсинг и мультиязычность

Архитектура парсера реализована по принципу расширяемости — каждый поддерживаемый язык обслуживается независимым модулем, что позволяет добавлять новые языки без модификации существующего кода. Диспетчер (`PARSERS_MAP`) направляет файл соответствующему парсеру на основе расширения.

| Язык | Инструмент | Основание |
|------|-----------|-----------|
| Python | `ast` (встроенный) | Нативная поддержка, высокая надёжность |
| JS/TS | Tree-sitter | Корректный парсинг современного синтаксиса |
| C++ | Tree-sitter | Сложный синтаксис, макросы |
| Go | Tree-sitter | Специфичный синтаксис |
| Java | Tree-sitter | Классовая структура |

#### 2.2.3. Генерация эмбеддингов

Используется одна модель эмбеддингов — `BAAI/bge-m3`. Она мультиязычная "из коробки" — одинаково хорошо работает и с русскими, и с английскими запросами против англоязычного кода, что снимает необходимость держать отдельные модели под каждый язык запроса или переводить запрос перед поиском.
Обоснование выбора модели представлено в разделе 4.1.

**Почему не нормализуем идентификаторы перед эмбеддингом**

Мы сознательно **не приводим имена функций/переменных к нижнему регистру и не убираем подчёркивания** перед тем, как отправить текст в модель эмбеддингов. Модель `bge-m3` обучена на большом корпусе исходного кода и уже понимает паттерны именования (`camelCase`, `snake_case`, аббревиатуры вроде `db`, `crud`), поэтому искусственная нормализация скорее теряет сигнал, чем помогает — оригинальное написание идентификатора само по себе несёт смысл для модели.


**Почему ChromaDB**

Для хранения векторов выбрана **ChromaDB** — `PersistentClient` хранит индекс локально на диске без необходимости поднимать отдельный сервер базы данных (в отличие от, например, Qdrant или Milvus в серверном режиме). Для масштаба задачи (один проект, ~150–250 чанков) это даёт быстрый старт без лишней инфраструктуры, при этом поддерживает косинусное сходство «из коробки» (`hnsw:space: cosine`).

### 2.3. Компонент поиска

#### 2.3.1. Гибридный поиск: почему не только векторный

Чисто семантический поиск иногда упускает точные совпадения идентификаторов — например запрос с точным именем функции (`create_access_token`) может не попасть в топ-5 по чистому косинусному сходству, если эмбеддинг «размыл» этот сигнал. Поэтому поверх dense-поиска добавлен **BM25** (`rank_bm25`) — классический полнотекстовый поиск по токенам, который хорошо находит точные лексические совпадения.

Результаты обоих методов нормализуются (min-max scaling) и объединяются линейно:

```
score = alpha · dense_score + (1 − alpha) · bm25_score
```

Параметр `alpha` настраивается прямо в интерфейсе (страница «Расширенные настройки»).

**Подбор alpha — сравнение на eval-датасете:**

| alpha | Precision@5 |
|---|---|
| 0.5 | 0.667 |
| 0.8 | **0.778** |

Финальное значение — **0.8** (80% вес у векторного поиска, 20% у BM25): семантический поиск даёт основной вклад в точность, BM25 подстраховывает на запросах с точными терминами.


### 2.3.2 Валидация и обработка текстовых данных

Перед генерацией эмбеддингов чанк проходит через сборку обогащённого текста: путь к файлу + язык + тип символа (функция/класс/метод) + docstring (если есть) + код. Файлы, которые не парсятся (синтаксические ошибки, бинарные файлы по ошибке в выборке) — пропускаются с предупреждением в лог, не прерывая индексацию остальной базы.
Индексация устойчива к ошибкам в отдельных файлах — синтаксические ошибки парсинга логируются и пропускаются без прерывания всего пайплайна (try/except в RAG/index.py).

### 2.4. LLM-интерпретация

Для генерации объяснений используется облачный API Groq с моделью `llama-3.1-8b-instant`. Выбор обусловлен следующими факторами:

1. **Скорость инференса:** 1-3 секунды против 10+ секунд для локальных альтернатив
2. **Доступность:** бесплатный тариф с достаточными лимитами
3. **Качество:** Llama 3.1 демонстрирует высокую точность в задачах анализа кода

Температура генерации установлена на уровне 0.3, что обеспечивает баланс между детерминированностью ответа и естественностью формулировок. Промпт содержит явное требование не выдумывать функциональность, отсутствующую в предоставленном контексте.

## 3. Экспериментальная методология

### 3.1. Датасет

Оценка качества выполнялась на эталонном наборе из 15 запросов, предоставленном организаторами чемпионата. Характеристики датасета:

| Параметр | Значение |
|----------|----------|
| Всего запросов | 15 |
| Язык запросов | 8 RU, 7 EN |
| Сложность | 5 Easy, 6 Medium, 4 Hard |
| Категории | auth, api, db, config, errors, business_logic, validation |
| Эталонов на запрос | 1-3 (медиана: 2) |

### 3.2. Метрики оценки качества

Для количественной оценки эффективности поисковой системы использовались две стандартные метрики информационного поиска: **Precision@5** (обязательная, согласно условиям кейса) и **MRR** (дополнительная, введённая для более глубокого анализа поведения системы). Каждая из метрик отвечает на свой исследовательский вопрос и даёт взаимодополняющую информацию о качестве ранжирования.

---

#### 3.2.1. Precision@5 — точность в топ-5

**Определение:** Precision@5 измеряет долю релевантных документов среди первых пяти результатов поиска.

$$ \text{P@5} = \frac{|\{\text{релевантные документы}\} \cap \{\text{топ-5 документов}\}|}{\min(5, |\{\text{релевантные документы}\}|)} $$

**Нормализация:** знаменатель равен $\min(5, \text{total\_relevant})$, что гарантирует максимальный балл 1.0 при нахождении всех релевантных документов в топ-5, независимо от их общего числа. Это критично для корректной оценки запросов с переменным числом эталонов (от 1 до 3 в нашем датасете).

**Интерпретация:**

| Значение | Интерпретация |
|----------|---------------|
| P@5 = 1.0 | Все ожидаемые фрагменты найдены в первых пяти позициях |
| P@5 = 0.5 | Половина ожидаемых фрагментов найдена |
| P@5 = 0.0 | Ни одного релевантного фрагмента в топ-5 |

**Целевой порог по условиям кейса:** ≥ 0.60.

---

#### 3.2.2. MRR — средний обратный ранг

**Определение:** MRR измеряет, **насколько высоко** в выдаче находится первый релевантный документ. Метрика чувствительна к порядку ранжирования и отражает практический пользовательский сценарий, в котором наиболее важен именно первый успешный результат.

$$ \text{MRR} = \frac{1}{N} \sum_{i=1}^{N} \frac{1}{\text{rank}_i} $$

где $\text{rank}_i$ — позиция первого релевантного документа для $i$-го запроса (если релевантный документ не найден, $\text{rank}_i = \infty$, вклад в сумму равен 0).

**Интерпретация:**

| Значение | Интерпретация |
|----------|---------------|
| MRR = 1.0 | Для всех запросов первый релевантный документ найден на позиции №1 |
| MRR = 0.5 | В среднем первый релевантный документ находится на 2-й позиции |
| MRR = 0.33 | В среднем на 3-й позиции |
| MRR = 0.0 | Ни для одного запроса не найден релевантный документ |

**Почему MRR добавлена, несмотря на то что не является обязательной:**

1. **Дополняет Precision@5** — Precision@5 отвечает на вопрос «сколько», а MRR — на вопрос «насколько высоко». Это разные аспекты качества, и их совместное использование даёт более полную картину.

2. **Отражает пользовательский опыт** — в типичном сценарии пользователь смотрит первые результаты; если правильный ответ сразу на первом месте, задача решена максимально быстро. MRR напрямую измеряет этот сценарий.

3. **Позволяет выявить паттерны** — в ходе эксперимента мы обнаружили, что русскоязычные запросы показывают более высокий MRR при более низком Precision@5, что указывает на более «сфокусированное» ранжирование (см. раздел 4.3).

---

#### 3.2.3. Допуск при сравнении идентификаторов

При сопоставлении предсказанных и эталонных `chunk_id` допускается отклонение в номере строки в пределах **±2 строк**. Это нивелирует незначительные расхождения в парсинге, вызванные особенностями работы `ast` и Tree-sitter (например, разное определение начала функции при наличии декораторов или многострочных сигнатур).

**Пример:** эталон `gymhero/security.py:create_access_token:12` считается совпавшим с предсказанным `gymhero/security.py:create_access_token:14`, так как разница в строках составляет 2.

Данный допуск реализован в `score.py` и применяется автоматически при вычислении обеих метрик.

---

#### 3.2.4. Связь метрик с архитектурными решениями

Выбор метрик не случаен — каждая из них проверяет определённое архитектурное решение:

| Метрика | Что проверяет | Связанное архитектурное решение |
|---------|---------------|--------------------------------|
| **Precision@5** | Способность системы находить все релевантные фрагменты в пределах топ-5 | Гибридный поиск (dense + BM25), обогащение чанков |
| **MRR** | Способность системы ставить релевантный фрагмент на высокую позицию | Качество эмбеддингов, точность ранжирования |
| **Разница RU/EN** | Кросс-языковую эффективность | Выбор мультиязычной модели `bge-m3` |
| **Разница по сложности** | Устойчивость к сложности запроса | Стратегия чанкинга, обогащение контекстом |

### 3.3. Процедура валидации

1. Для каждого вопроса из `eval_questions.json` выполняется поиск с использованием гибридного ретривера
2. Формируется `results.json` с топ-5 идентификаторами чанков
3. Запускается `score.py`, который сопоставляет предсказанные и эталонные чанки с учётом допуска по строкам
4. Вычисляются агрегированные метрики с разбивкой по языку и сложности

## 4. Результаты и обсуждение

### 4.1. Выбор модели эмбеддингов

На отборочном этапе выполнено сравнение трёх моделей эмбеддингов на идентичных данных:

| Модель | Размерность | HitRate@5 | Точность RU | Точность EN |
|--------|-------------|-----------|-------------|-------------|
| MiniLM-L12-v2 | 384 | 0.78 | 0.62 | 0.71 |
| LaBSE | 768 | 0.89 | 0.81 | 0.83 |
| **BGE-m3** | **1024** | **1.00** | **0.86** | **0.91** |

**Интерпретация:** BGE-m3 демонстрирует превосходство по всем метрикам. Ключевым фактором является мультиязычная природа модели, позволяющая обрабатывать русскоязычные запросы без потери точности. Дополнительный выигрыш даёт обогащение текста чанка контекстной информацией — прирост точности составил до 16% относительно подачи «голого» кода.

### 4.2. Оптимизация гиперпараметра α

Экспериментальный подбор баланса между векторным и лексическим поиском:

| α | Описание | Precision@5 |
|---|----------|-------------|
| 0.0 | Только BM25 | 0.512 |
| 0.3 | Преобладание BM25 | 0.588 |
| 0.5 | Сбалансированный | 0.667 |
| 0.7 | Преобладание dense | 0.733 |
| **0.8** | **Оптимальный** | **0.778** |
| 1.0 | Только векторный | 0.711 |

**Интерпретация:** увеличение веса плотного поиска до 0.8 даёт максимальную точность. При α=1.0 наблюдается снижение, что подтверждает необходимость лексической компоненты для запросов с точными идентификаторами.

### 4.3. Итоговые метрики

**Ключевой результат:** система достигла Precision@5 = 0.778, что превышает целевой порог (≥0.60), установленный в условиях кейса.

**Основные результаты:**

| Метрика | Значение |
|---------|----------|
| **Precision@5** | **0.778** |
| **MRR** | **0.728** |

**Детализация по языку запроса:**

| Метрика | Overall | RU | EN |
|---------|---------|----|----|
| Precision@5 | 0.778 | 0.708 | 0.857 |
| MRR | 0.728 | 0.792 | 0.655 |

**Детализация по сложности (Precision@5):**

| Сложность | Значение |
|-----------|----------|
| Easy | 0.900 |
| Medium | 0.806 |
| Hard | 0.583 |

### 4.4. Обсуждение

**Ключевые факторы успеха:**

1. **Обогащение текста чанка** (путь + имя символа + docstring) обеспечило наиболее значимый прирост точности относительно baseline.
2. **Гибридный ретривер** с оптимальным α=0.8 превзошёл как чисто векторный, так и чисто лексический подходы.
3. **Мультиязычная модель** позволила достичь стабильно высоких результатов на обоих языках запросов.

**Наблюдаемые ограничения:**

- Более низкий результат на русском языке (0.708 против 0.857) объясняется тем, что код и документация в `gymhero` написаны на английском, создавая лексическое преимущество для англоязычных запросов.
- Снижение точности на сложных вопросах (0.583) указывает на необходимость более глубокого семантического понимания многошаговых запросов.

## Как запустить

### 1. Установка зависимостей

```bash
git clone <repo_url>
cd rt-ai-championship-stage2
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

### 2. Индексация кодовой базы

```bash
python RAG/index.py dataset/gymhero
```

Скрипт сканирует поддерживаемые файлы, извлекает функции/классы/методы, обогащает текст чанка путём и именем символа, генерирует эмбеддинги (`BAAI/bge-m3`) батчами по 8 и сохраняет в ChromaDB. Существующая коллекция автоматически очищается перед переиндексацией во избежание дублей.

Шаг 1: Сканирование файлов в dataset/gymhero/
        ↓
Шаг 2: Парсинг каждого файла (ast/Tree-sitter) → извлечение функций/классов
        ↓
Шаг 3: Обогащение текста (путь + имя символа + docstring + код)
        ↓
Шаг 4: Генерация эмбеддингов батчами по 8 (модель bge-m3)
        ↓
Шаг 5: Сохранение в ChromaDB + бэкап в chunks.jsonl


### 3. (Опционально) Подключение LLM-чата

```bash
# 1. Зарегистрируйтесь на https://console.groq.com (через Google)
# 2. API Keys → Create API Key
# 3. В терминале перед запуском:
export GROQ_API_KEY="ваш_ключ"
```

Без ключа всё остальное (поиск, метрики) работает нормально — чат покажет понятное предупреждение вместо ответа.

### 4. Запуск интерфейса

```bash
streamlit run RAG/ui/app.py
```

Откроется на `http://localhost:8501`. Три страницы: **Поиск**, **Чат с LLM**, **Расширенные настройки** (баланс alpha, выбор модели, расчёт метрик P@5/MRR).

### 5. Воспроизведение метрики

```bash
python accuracy_checking/generate_results.py --alpha 0.8
python score.py --predictions accuracy_checking/results.json --questions accuracy_checking/eval_questions.json
```

## GitHub-процесс: CI, Kanban, шаблон PR

- **CI** (`.github/workflows/ci.yml`) — на каждый push прогоняется `ruff check .`, гарантируя единый стиль импортов и кода у всех участников команды
- **Kanban-доска** в GitHub Projects — задачи распределены по колонкам Backlog / In Progress / Review / Done, каждая привязана к Issue и закрывается автоматически через `closes #N` при мерже PR
- **Шаблон Pull Request** (`.github/pull_request_template.md`) — каждый PR описывает что сделано, какие файлы затронуты, что осталось на будущее, и чек-лист тестирования перед мержем
