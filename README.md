## Архитектура

```
Запрос пользователя (RU / EN)
        │
        ▼
┌────────────────────┐
│  bge-m3 embedding   │──── векторный (dense) поиск — ChromaDB
└────────────────────┘
        │
        ├──────────────┐
        ▼              ▼
   Dense search    BM25 (rank_bm25, поверх chunks.jsonl)
        │              │
        └──── alpha ────┘
              │ линейный рескоринг:
              │ score = alpha · dense + (1 − alpha) · BM25
              ▼
        Топ-5 фрагментов кода
              │
              ▼  режим «Чат с LLM»
        Groq API (llama-3.1-8b-instant, temperature=0.3)
              │
              ▼
     Объяснение на русском со ссылками на источники
```

## Архитектурные решения и их обоснование

### Стратегия чанкинга

Код разбивается на чанки **по функциям и классам** (через `def`/`class`), а не по фиксированному числу строк — это даёт каждому чанку завершённую логическую единицу, которую можно осмысленно объяснить и процитировать. Помимо самого тела функции в текст чанка добавляются путь к файлу и имя символа — это даёт модели больше контекста при построении эмбеддинга, чем голый код без подписи.

> Дополнительно к функциям/классам в индекс может попадать содержимое всего файла как отдельный модульный чанк — подробное описание этого механизма и его назначения см. в комментариях `RAG/chunker/parsers/py_parser.py` (реализовано Димой).

### Почему bge-m3?

Используется одна модель эмбеддингов — `BAAI/bge-m3`. Она мультиязычная "из коробки" — одинаково хорошо работает и с русскими, и с английскими запросами против англоязычного кода, что снимает необходимость держать отдельные модели под каждый язык запроса или переводить запрос перед поиском.

Выбор модели эмбеддингов сделан на основе сравнения трёх кандидатов, проведённого на **отборочном этапе** чемпионата (кейс «Навигатор по смыслу»): `paraphrase-multilingual-MiniLM-L12-v2` (384), `sentence-transformers/LaBSE` (768) и `BAAI/bge-m3` (1024).

**Итоги сравнения с отбора:**

| Модель | Размерность | HitRate@5 | Точность RU | Точность EN |
|---|---|---|---|---|
| MiniLM-L12-v2 | 384 | ниже остальных | заметное падение на русских запросах | — |
| LaBSE | 768 | средний результат | стабильна | стабильна |
| **BGE-m3** | **1024** | **100%** | **85.71%** | **90.91%** |

BGE-m3 победила по всем измеренным метрикам сразу (HitRate, MRR, кросс-языковая стабильность, чёткость кластеризации на t-SNE), поэтому в финальном решении используется именно она.

**Что перенесли из отбора в финальное решение:** на отборочном этапе обогащение индексируемого текста именем функции и языком программирования дало прирост точности до +16%. Этот же принцип применён в `RAG/index.py` — текст чанка перед эмбеддингом обогащается путём к файлу, типом символа и docstring, а не подаётся как голый код (см. «Что повлияло на рост Precision@5» ниже).


### Почему не нормализуем идентификаторы перед эмбеддингом?

Мы сознательно **не приводим имена функций/переменных к нижнему регистру и не убираем подчёркивания** перед тем, как отправить текст в модель эмбеддингов. Модель `bge-m3` обучена на большом корпусе исходного кода и уже понимает паттерны именования (`camelCase`, `snake_case`, аббревиатуры вроде `db`, `crud`), поэтому искусственная нормализация скорее теряет сигнал, чем помогает — оригинальное написание идентификатора само по себе несёт смысл для модели.


### Почему ChromaDB

Для хранения векторов выбрана **ChromaDB** — `PersistentClient` хранит индекс локально на диске без необходимости поднимать отдельный сервер базы данных (в отличие от, например, Qdrant или Milvus в серверном режиме). Для масштаба задачи (один проект, ~150–250 чанков) это даёт быстрый старт без лишней инфраструктуры, при этом поддерживает косинусное сходство «из коробки» (`hnsw:space: cosine`).

### Гибридный поиск: почему не только векторный

Чисто семантический поиск иногда упускает точные совпадения идентификаторов — например запрос с точным именем функции (`create_access_token`) может не попасть в топ-5 по чистому косинусному сходству, если эмбеддинг «размыл» этот сигнал. Поэтому поверх dense-поиска добавлен **BM25** (`rank_bm25`) — классический полнотекстовый поиск по токенам, который хорошо находит точные лексические совпадения.

Результаты обоих методов нормализуются (min-max scaling) и объединяются линейно:

```
score = alpha · dense_score + (1 − alpha) · bm25_score
```

Параметр `alpha` настраивается прямо в интерфейсе (страница «Расширенные настройки»).

**Подбор alpha — сравнение на eval-датасете:**

| alpha | Precision@5 |
|---|---|
| 0.5 | 0.667 |
| 0.8 | **0.778** |

Финальное значение — **0.8** (80% вес у векторного поиска, 20% у BM25): семантический поиск даёт основной вклад в точность, BM25 подстраховывает на запросах с точными терминами.

### Мультипарсинговая архитектура

Парсер кода спроектирован расширяемо — не завязан жёстко на Python. Каждый поддерживаемый язык (`py`, `js`/`ts`, `cpp`, `go`, `java`) обслуживается **независимым модулем** в `RAG/chunker/parsers/`, который знает только свой синтаксис. Поверх них стоит диспетчер — словарь `PARSERS_MAP` и функция `collect_chunks_for_file()` в `RAG/chunker/router.py`, которая по расширению файла определяет, какому парсеру передать содержимое.


### Валидация и обработка текстовых данных

Перед генерацией эмбеддингов чанк проходит через сборку обогащённого текста: путь к файлу + язык + тип символа (функция/класс/метод) + docstring (если есть) + код. Файлы, которые не парсятся (синтаксические ошибки, бинарные файлы по ошибке в выборке) — пропускаются с предупреждением в лог, не прерывая индексацию остальной базы.
Индексация устойчива к ошибкам в отдельных файлах — синтаксические ошибки парсинга логируются и пропускаются без прерывания всего пайплайна (try/except в RAG/index.py).

### Почему Groq, а не локальная Ollama

Задание допускает как локальную LLM (Ollama + mistral:7b), так и облачную модель — выбрана **облачная (Groq, `llama-3.1-8b-instant`)**:
- не требует скачивания модели (~4 ГБ для mistral:7b)
- отвечает заметно быстрее (1–3 секунды против 10+ секунд на CPU у локальной модели)
- бесплатный тариф с высокими лимитами, без необходимости платной подписки

### Temperature = 0.3 в LLM

`temperature` управляет «случайностью» выбора слов моделью — от 0 (детерминированно, наиболее вероятные токены) до 1+ (более творчески, но менее предсказуемо). Для задачи объяснения кода это критично:

- модель не должна выдумывать функции или поведение, которых нет в переданном коде;
- должна точно ссылаться на реальные имена функций и файлы из контекста;
- должна давать стабильные ответы — если жюри на защите дважды задаст один и тот же вопрос, объяснения не должны кардинально расходиться.

При высокой температуре растёт риск, что модель «приукрасит» ответ деталями, которых не было в исходном коде. Поэтому выбрано низкое значение — **0.3**: достаточно низкое, чтобы держаться фактов из контекста, но не строго 0 (что иногда даёт излишне сухие, оборванные формулировки).

Промпт дополнительно явно требует не выдумывать функциональность — проверено на запросах про возможности, которых в `gymhero` нет (кэширование, OAuth, WebSocket, rate limiting): модель корректно отвечает «в коде это не реализовано», а не пытается притянуть смежные понятия (например логирование как «форму кэширования»).

## Что повлияло на рост Precision@5

В порядке вклада в итоговый результат:

1. **Обогащение текста чанка** (путь + имя символа + docstring, а не голый код) — самое заметное улучшение относительно baseline с чистым кодом
2. **Гибридный поиск vs чистый векторный** — добавление BM25 подняло точность на запросах с точными именами функций
3. **Подбор alpha** (0.5 → 0.8) — рост Precision@5 с 0.667 до 0.778 на одном и том же индексе, только за счёт перебалансировки веса между dense и sparse поиском
4. **Мультиязычная модель эмбеддингов** (bge-m3) — стабильно высокий результат на обоих языках запросов (RU 0.708, EN 0.857) без необходимости в переводе запроса

## Проверка точности — `accuracy_checking/`

Изолированный модуль оценки качества, отделённый от продакшен-кода интерфейса:

- **`eval_questions.json`** — эталонный набор из 15 вопросов от организаторов, с полями `correct_chunk_ids`, `difficulty`, `language`
- **`generate_results.py`** — прогоняет все 15 вопросов через `HybridSearcher`, сохраняет топ-5 в `results.json`
- **`results.json`** — финальный артефакт с предсказаниями (сгенерирован с `alpha=0.8`)
- **`score.py`** (корень репозитория) — считает Precision@5 и MRR, с разбивкой по сложности и языку для обеих метрик

Метрики можно пересчитать и прямо из интерфейса — страница «Расширенные настройки» → выбор метрики (Precision@5 / MRR) → кнопка «Рассчитать».

## Временные характеристики

| Операция | Время |
|---|---|
| Загрузка модели `bge-m3` (первый запуск) | ~5–10 сек |
| Один поисковый запрос (после загрузки) | ~1–6 сек |
| Ответ LLM (Groq) | ~1–3 сек |
| Полный цикл «вопрос → поиск → LLM-ответ» в чате | ~5–10 сек |
| Индексация `dataset/gymhero/` целиком | зависит от объёма; батчи по 8 чанков |

Указанные цифры — с локального запуска на ноутбуке без GPU; при недостатке RAM (< 8 ГБ) первая загрузка модели может занимать заметно дольше.

## Как запустить

### 1. Установка зависимостей

```bash
git clone <repo_url>
cd rt-ai-championship-stage2
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

### 2. Индексация кодовой базы

```bash
python RAG/index.py dataset/gymhero
```

Скрипт сканирует поддерживаемые файлы, извлекает функции/классы/методы, обогащает текст чанка путём и именем символа, генерирует эмбеддинги (`BAAI/bge-m3`) батчами по 8 и сохраняет в ChromaDB. Существующая коллекция автоматически очищается перед переиндексацией во избежание дублей.

Шаг 1: Сканирование файлов в dataset/gymhero/
        ↓
Шаг 2: Парсинг каждого файла (ast/Tree-sitter) → извлечение функций/классов
        ↓
Шаг 3: Обогащение текста (путь + имя символа + docstring + код)
        ↓
Шаг 4: Генерация эмбеддингов батчами по 8 (модель bge-m3)
        ↓
Шаг 5: Сохранение в ChromaDB + бэкап в chunks.jsonl


### 3. (Опционально) Подключение LLM-чата

```bash
# 1. Зарегистрируйтесь на https://console.groq.com (через Google)
# 2. API Keys → Create API Key
# 3. В терминале перед запуском:
export GROQ_API_KEY="ваш_ключ"
```

Без ключа всё остальное (поиск, метрики) работает нормально — чат покажет понятное предупреждение вместо ответа.

### 4. Запуск интерфейса

```bash
streamlit run RAG/ui/app.py
```

Откроется на `http://localhost:8501`. Три страницы: **Поиск**, **Чат с LLM**, **Расширенные настройки** (баланс alpha, выбор модели, расчёт метрик P@5/MRR).

### 5. Воспроизведение метрики

```bash
python accuracy_checking/generate_results.py --alpha 0.8
python score.py --predictions accuracy_checking/results.json --questions accuracy_checking/eval_questions.json
```

## Известные ограничения

- Чат с LLM требует интернет (Groq — облачный API, не локальная модель)
- Первый поисковый запрос после запуска занимает дольше остальных (загрузка модели `bge-m3` в память, кэшируется через `@st.cache_resource`)
- RU-вопросы получают чуть более низкий Precision@5 (0.708) по сравнению с EN (0.857) — вероятно из-за того, что весь код и docstring'и в `gymhero` написаны на английском, что даёт лексическое преимущество англоязычным запросам

## Возможные улучшения (не реализовано)

- **Cross-encoder reranking** — переранжирование топ-20 кандидатов более точной (но медленной) моделью перед финальным топ-5; идея зафиксирована, не реализована из-за ограничения по времени
- **Кэширование запросов** — повторные одинаковые запросы пока пересчитываются заново; кэш на уровне эмбеддинга запроса мог бы ускорить повторные обращения
